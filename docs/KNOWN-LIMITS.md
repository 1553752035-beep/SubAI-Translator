# 已知限制与验收口径

> 最后更新：2026-10-18

## 一、识别（ASR）

### 1. 空洞的权威拆解（1:40 直播素材，用户逐段听音确认）

8 处 ≥2.5s 空洞 = 42.1s，其中 7 段物理上有人声（38.8s / 92.2%）。**但"有人声"不等于"该被识别"**：

| 类别 | 段落 | 时长 | 说明 |
|---|---|---|---|
| 多人/水友/听不清 | 1、3、6 | 14.3s | 已知限制（非主说话人、远场、模糊）|
| 非语音：拉长音/喊叫 | 2、7、8 | 20.7s | "year"拉长音、成功失败瞬间的高音量喊叫；**任何 ASR 都大概率不识别** |
| 真无人声 | 5 | 3.4s | 正常留白 |
| 疑似漏句 | 4（"这是哪"）| 3.8s | **验证后否认定为系统性缺陷**（见下）|

#### 「这是哪」的验证（重要）
该句在**某一次任务运行**里缺失，但后续 6 种配置 + 3 次重复全部识别：
切片(VAD/无VAD) / 整段(VAD/无VAD) / word_timestamps 开关 / condition_on_previous_text 开关 / 连跑 3 次 —— **100% 命中**。

**结论**：这是 **ASR 偶发漏句（非确定性）**，不是 VAD、阈值、模型能力问题；重跑通常能补回。
**验收含义**：涉及"漏识别"的判断，必须**同配置跑 ≥3 次取多数**，不能拿单次空洞当系统性缺陷。

#### 固定 language=zh 的代价（有意为之）
真实的英文感叹词（如通关时喊的那声 "yes"）会被忽略——这是消除"中文音频凭空产出整段英文"幻觉的代价。
**不要改回自动语言检测**：自动检测换来的英文幻觉，代价远大于丢几声感叹词。

**根本解（多人场景）**：说话人分离（diarization），列为"未来增强"，不在当前优先级。

### 2. 专有名词仍可能被听成常见词
**现象**：主播名"橘长"被听成"局长/区长/队长"。
**缓解**：上传页填「专有名词」词表 + 拼音同音纠正（自动纠正 / 近音只提示）。
**注意**：单字简称（如"洲"）不在同音纠正范围（无共同汉字会被过滤）。

### 3. turbo 模型质量（样本仅 4 条，口径严格）
| 抽查 | 原文 | turbo 输出 | 评价 |
|---|---|---|---|
| 1 | 手脚都是汗吗 | 这些都是汗吗? | 部分对（"手脚"丢了）|
| 2 | 路呢 | 鲁呢? | 同音（音对字错）|
| 3 | 我到第3关了 | 我到第3关了。 | 完全正确 |
| 4 | 即使是黑白丝美少女都有 | 据说黑白丝每胜利都有 | 部分对（语义偏差）|

**结论**：比 small 明显更准（RTF 也快 4.5 倍），但**仍会错识别**。样本量不足，需继续累积。

## 二、验收口径（必须按此报告）

### 0. ASR 非确定性规则（适用于**所有** ASR 指标）

ASR 是非确定性的（同一音频每次运行输出不同）。因此所有 ASR 相关验收指标——
漏识别、专有名词命中率、覆盖率、错字率——必须同时满足：

1. **同一次运行对齐**：指标值必须来自同一次运行的 `<stem>.asr-raw.srt`（原始文本）+
   纠正日志 + `<stem>.bilingual.srt`（最终字幕），禁止跨轮次比较或拿历史文件凑数。
2. **≥3 次取多数**：涉及"有无识别"的判定（某句是否漏了、某词是否命中），
   必须同配置跑 ≥3 次取多数，**不能拿单次结果当结论**。

> 教训：曾因跨轮次比较误判"鲁长归零"，又因单次空洞差点把偶发漏句写成系统性缺陷。

### 1. 禁止跨轮次比较
ASR 是非确定性的（同一视频每次输出不同）。所有指标必须基于**同一次运行**的：
- `<stem>.asr-raw.srt`（纠正前原文，已落盘）
- 纠正日志（`[词表] ...`）
- `<stem>.bilingual.srt`（最终字幕）

### 2. 覆盖率口径
- **当前报告值**：`[ASR 覆盖] 音频 X s / 字幕覆盖 Y s（Z%）/ 留白 W s / ≥2.5s 空洞 N 处`
- **含义**：字幕覆盖时长 ÷ 音频总时长，能发现漏识别
- **不是**"VAD 检出段保留率"（faster-whisper 不暴露 VAD 段数）
- **必须标注"观察模式下的值"**：当前不删行，阈值生效后该值会变

### 3. 专有名词指标
- **命中率**：词表词在最终字幕里正确出现的次数
- **误纠率**：自动纠正（auto）里改错的次数
- 两者必须同时看，只看命中率会掩盖误伤

## 三、本地翻译模式（StreamRevise）

### 支持的模型与启动
- `Hy-MT2-1.8B-StreamRevise-Q4_K_M.gguf`（1.07 GB），用 koboldcpp 加载：
  `koboldcpp.exe --model <gguf> --port 5001`（**最小参数即可**；`--quiet`/`--skiplauncher` 会被当成位置参数报 `model_param` 冲突）

### 配置（四个环境变量）
```
SUBAI_LLM_MODE=local
SUBAI_LLM_LOCAL_URL=http://127.0.0.1:5001/v1/chat/completions   # 代码会自动改用 /v1/completions
SUBAI_LLM_BATCH_SIZE=1
SUBAI_LLM_RAW_MODE=true
```

### 实测表现（1:40 直播素材，33 行）
| 项 | 结果 |
|---|---|
| 速度 | 4.5s（0.137s/行）→ 1 小时约 **2.7 分钟** ✅ |
| 未翻译 / 截断 | **0** |
| 拼接异常（DonDon't 类）| **0** |
| 术语注入 | 生效（局长→Captain）|
| 否定/情态句 | **10/12** |
| **错译** | **4/33（1–20 行窗口内 3 处）** —— 超「≤2 处/20 行」标准 |

### 已知质量风险（写清楚，便于对号入座）
1. **「你能不能 + 动词」句式**：否定方向可能反转（`你能不能掉到一层` → `Could you not fall`）。
   游戏指令类场景（"你能不能别送/你能不能撤"）**建议人工复核或送云端**。
2. **未进词表的人名/专有名词**：可能被意译（`我操武` → `martial artist`）；填词表可解。
3. **口语/俚语**：弱于云端（`我要气笑了` → `laugh my head off`，丢了"气"）。

### 集成踩过的坑（改配置/换模型必看）
- **raw 指令必须用语言全名**（`English`），不能用代码（`en`）——本地模型不懂 `en`，
  实测会**整句原样不翻译**。云端能理解代码，本地不能。
- `_translate_one` 必须传 `system_extra=ctx_block`，否则**术语注入失效**（局长→Director 而非 Captain）。
- **`DonDon't` / `WeWe` / `GG` 这类怪输出不是模型 bug，是 chat 端点套错模板的产物**。
  遇到"稳定复现的怪输出"，**先换端点（raw vs chat）对照一次再下结论**——
  raw completion 下这些全部消失。
- 批量协议：StreamRevise **只做单句直译**，多行编号会返回空；单行编号可以但会多一次回退请求，
  所以 `BATCH_SIZE=1` 时应直接走单句路径。
### 模型选型（2026-10-18 实测，重要）

| 模型 | 速度（1 小时视频）| 错译（33 行）| 批量编号协议 | 推荐 |
|---|---|---|---|---|
| **Hy-MT2-1.8B 基座**（Q4_K_M，1.13 GB）| **1.9 分钟** | **2/33（1–20 行窗口 0 处）** | ✅ 支持 | **本地默认** |
| Hy-MT2-1.8B-**StreamRevise**（流式版，1.07 GB）| 2.7 分钟 | 4/33（窗口 3 处）| ❌ 不支持 | 仅流式字幕场景 |

**基座配置（推荐）**：
```
SUBAI_LLM_MODE=local
SUBAI_LLM_LOCAL_URL=http://127.0.0.1:5001/v1/chat/completions
SUBAI_LLM_BATCH_SIZE=10
SUBAI_LLM_RAW_MODE=false
```

基座修好了 StreamRevise 的两个硬伤：
- `我要气笑了` → `laugh in anger`（不再丢"气"）
- **`你能不能` 否定反转消失**（`Can you fall` 而非 `Could you not fall`）

基座残余错译（2/33，均在第 20 行之后）：
- `局长快传送到头上了` → `reaching the top`（丢了"传送"）
- `局长你去他第一` → `you are first`（意不准确）

### 量化选型（2026-10-18 A/B）

Q4_K_M（1.08 GB）vs Q6_K（1.41 GB），同 33 行：

| 维度 | Q4_K_M | Q6_K |
|---|---|---|
| 速度 | 3.2s → **1.9 分钟/小时** | 3.8s → 2.3 分钟（慢 19%）|
| 「你能不能」否定句 | ✅ `Can you fall` | ❌ `Can't you drop`（退化）|
| 「我要气笑了」 | ✅ `laugh in anger` | ❌ `getting angry`（丢"笑"）|
| 语序/完整性 | 一般 | ✅ 更好 |

**结论：保持 Q4_K_M**。游戏解说里「你能不能 X」是高频指令句，**否定反转比语序瑕疵严重得多**。

### RAG 的取舍（2026-10-18 判断）

- **外部语料 RAG（OpenSubtitles / MuSC 等影视字幕）对本项目是负收益**：
  影视剧是书面化完整句，游戏解说是口语/省略/玩梗，检索结果可能把模型往书面向拉
  （已有反向证据：云端 `It's pee` vs 本地 `It's urine`，云端更口语）。
- **自有翻译记忆（TM）的语义检索才是正路**：只检索「用户确认过/改过的译文」，
  保证跨视频、跨系列的术语与风格一致。当前已部分实现（术语包 + 翻译缓存 + 摘要 terms）。
- **暂不做**：当前 2/33 已达标，那 2 处是语序/省略问题；RAG 需要向量库 + 嵌入模型 +
  检索逻辑（~200 行）。等真实使用后出现"某些句式/术语反复错"再上，收益才是实的。

## 五、测试基线与环境（2026-10-24 实诊）

### 结论先行

| 环境 | 结果 |
|---|---|
| Python 3.12（2026-10-17，文档原记录） | 后端 487 passed、前端 51 passed、零跳过 |
| **Python 3.14.3 + httpx 0.28.1（2026-10-24，修复后）** | **后端 508 passed、0 failed** |

### 19 个失败的真正根因：宿主 NO_PROXY 里的 [::1]

现象：webhook / openapi / 插件安装 / 翻译 HTTP / 两组 e2e 共 19 个用例集体报
httpx.InvalidURL: Invalid port: ':1]'。

实诊（2026-10-24）：

```
NO_PROXY=localhost,127.0.0.1,::1,[::1]   -> httpx trust_env=True 抛 Invalid port: ':1]'
NO_PROXY=localhost,127.0.0.1,::1         -> 200 OK
httpx.post(..., trust_env=False)         -> 200 OK
```

httpx 在 trust_env=True 时会把 NO_PROXY 的每一项按 URL 解析，**带方括号的 IPv6 写法 `[::1]`**
被解析成 port=':1]' 直接抛错。这些用例都依赖本地 mock HTTP 服务，于是集体失败。

### 修复（三层）

1. **产品层（最重要）**：`src/config.py` 新增 `normalize_no_proxy()`，在模块导入期（早于任何 httpx 调用）
   去掉方括号。**这不是测试专用修复**——自检 `subai-backend.exe --check` 的「翻译后端端点连通性」
   在脏 NO_PROXY 下同样报 `InvalidURL: Invalid port: ':1]'`，意味着**任何 NO_PROXY 含 `[::1]` 的机器，
   连本地 koboldcpp 和云端 API 都会失败**，且错误信息完全指向不了真因。修后同样条件下变为
   `ConnectError: 目标计算机积极拒绝`（真实连接失败），koboldcpp 起来后直接 PASS（1149.5ms）。
2. **测试层**：`tests/conftest.py` 在 collection 期调用同一归一化，测试不受宿主配置影响。
3. **环境层**：本机 `HKCU\Environment` 的 `NO_PROXY` / `no_proxy` 改为 `localhost,127.0.0.1,::1`。

修复后验证：此前失败的 5 个文件 37 passed、两组 e2e 7 passed、全量 **508 passed / 0 failed**。

### 双端翻译验收（2026-10-24，按用户既定规则）

| 端 | 配置 | 3 句耗时 | 代表输出 |
|---|---|---|---|
| 本地 | koboldcpp + Hy-MT2-1.8B-Q4_K_M @5001 | 1.9s | `我操武这波真的太秀了` → `This move of Wu is really amazing` |
| 云端 | DeepSeek `deepseek-chat` | 2.4s | 同上 → `Wu really popped off this time` |

两边均 0 失败行。云端口语化/游戏术语明显更贴（feeding、popped off、right on top of us），
本地会把「送」译成 sending 而非 feeding，与既有选型结论一致（云端优先，本地作离线兜底）。

### 重要更正（写下来防止重犯）

我最初把根因判成「Python 3.14 + httpx 0.28.1 依赖漂移」，并一度写进本文档与 README。
**那是错的**：同样的 httpx 0.28.1 在干净 NO_PROXY 下 100% 通过。教训——
多个不相干模块同时报同一个底层异常时，先怀疑**共同的环境输入**（代理、编码、时区、路径分隔符），
再怀疑依赖版本。

### 与 LLM / 模型无关

这 19 个用例全部使用本地 mock OpenAI 服务（见 test_pipeline_e2e_full 的 docstring），
**不需要真实 LLM 或 API Key**。真正需要外部 LLM 的只有手工联调与 bench 脚本。
