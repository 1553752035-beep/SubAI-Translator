# 调研教训（LESSONS）

> 这份文件记录**方法论层面的教训**，不是功能清单。
> 每一条都来自一次真实的判断失误，写明「当时怎么想的 / 错在哪 / 以后怎么做」。
> 功能与架构决策写进 `项目总方案.md`，这里只写「怎么想错了」。

---

## L-001 不要用无信息量的素材做能力对比

**场景**：评估 SenseVoice 能否改善中文游戏喊话识别。

**当时的做法**：拿 `Delta Force 2026.04.08` 里 37 秒的糊音频切片做 A/B。
whisper 出 6 个汉字，SenseVoice 出 6 个汉字，于是判定「换引擎没有提升，建议砍掉」。

**错在哪**：
那段音频**本身就只含 6 个字的信息量**。两个引擎都只说出 6 个字，
不是「能力相同」，是**这段素材根本没有可供区分的特征**。
用一段谁都做不对的题，得出「谁都做不对」的结论，再据此砍掉方向——
这是把**测试设计的缺陷**误读成**被测对象的结论**。

换到语音密集的素材（`2026.09.24`，81 条字幕）后：
whisper 158 字碎片 vs SenseVoice 289 字完整句，差异立刻显现。

**以后怎么做**：
- 能力对比必须用**该能力能发挥作用的样本**。测抗噪就用有噪声的，测中文就用地道中文，
  测长句就用长句——**先确认样本里有可区分的信息量，再设计对照组**。
- 判断「样本够不够格」的方法：先让**一个已知最强的实现**跑一遍。
  它也只能出零星几个字，说明是样本问题，不是方案问题。
- 结论写作模板：「在 X 类素材上，A 与 B 无差异」——**必须带限定语**。
  不能由「某一段无差异」推出「这个方向没有价值」。

## L-002 拿对方方案做对比前，先读对方的文档

**场景**：同上。当时准备「自建 SenseVoice provider」。

**当时的做法**：直接从 PyPI 和 GitHub 找 SenseVoice 模型，用 `funasr` 库跑起来，
踩了一堆坑（VAD 不传 `vad_model` 只处理开头几秒、整段合并成一条、参数怎么调都不对），
还一度得出「SenseVoice 比 whisper 差」的错误结论。

**错在哪**：
同类项目 SmartSub 的 README 里**明写了三件事**，我是在踩完全部坑之后才读到的：
1. 他们**不用 `funasr` 库**，用 `sherpa-onnx` 原生库（1.13.2）；
2. VAD 用 **Silero**（随包内置），不是 funasr 的 fsmn-vad；
3. 有 **GTCRN 降噪**，我完全没考虑；
4. 还有 **Paraformer-zh**（中文专精），我压根没测。

他们的 `docs/guides/engines/funasr.md` 甚至直接写了我们争论的那个问题：
> **时间轴粒度**：FunASR 系无词级时间戳，长句拆分按文本比例兜底

**以后怎么做**：
- **先读文档，再动手**。尤其是：技术选型表、已知限制章节、常见问题章节。
- 别人成熟的项目里，「已知限制」那一栏往往就是**你已经踩到或即将踩到的坑**。
- 别人的代码注释里有大量「我们踩过这个坑」的记录，那是**免费的经验**：
  例如他们记录了「Windows 用户名含中文 → 原生库打不开 → VAD 静默得到 vad is nullptr」，
  而我们项目的路径恰好含中文。

## L-003 复刻对比实验时，参数必须逐项对齐

**场景**：第一次 whisper vs SenseVoice 对比。

**当时的做法**：whisper 侧用 `initial_prompt=None`，SenseVoice 侧配置随意。

**错在哪**：
项目 `pipeline.py:292` 实际传的是：
`initial_prompt="以下是普通话的句子，请用简体中文转写。"`

少了这个 prompt，whisper 输出繁体「有敵人」；加上后输出简体「有敌人」。
我差点把「我自己漏了参数」当成「模型能力差异」写进结论。

**以后怎么做**：
- 对比实验前，**先把被测系统在真实调用点的完整参数抄下来**（读源码，不是凭印象）。
- 对齐清单：语言、prompt、VAD、beam、温度、阈值、精度（int8/float16）、线程数、模型文件版本。
- 任何一处没对齐，结论里必须写「此项未对齐，可能影响结果」。

## L-004 不要只数「字数」，要看「内容对不对」

**场景**：SenseVoice 出 289 字 vs whisper 出 158 字。

**当时的风险**：容易直接下结论「字数多 = 更好」。

**实际情况**：
- SenseVoice 多的字里，**大部分是对的**：「打虎蹲」（whisper 作「打虎顿」）、
  「放烟花了」（whisper 作「放鸭花」）、「火包」（whisper 作「火锋」）、
  「逗逼呢」（whisper 作「都逼了」）；
- 但也有**胡编的部分**：开头一整段「玩比家领先什么新头部啥的，毕竟当时我跟这个五猫玩啊」
  在原始音频里找不到对应，像模型在「发挥」；
- 还有数字错误：「吃8吃8」。

**即：字数多 ≠ 更准，可能只是「更敢猜」。**

**以后怎么做**：
- 质量评估至少三个维度：**召回**（该有的有没有）、**精确**（说了的有没有说错）、**可读性**（能不能直接看）。
- 逐条对照原文听一遍，标出「对的 / 错的 / 编的」三类，再算比例。
- 「敢猜」和「准确」是两种不同的产品取向，**不是优劣**：
  游戏喊话需要敢猜（碎片没法看），严肃文本需要保守（编造代价高）。
  所以正确答案往往是**可切换**，而不是二选一。

## L-005 用户说「看完了吗」的时候，通常是真的没看完

**场景**：读 SmartSub 文档。

**当时的情况**：读了 README 的主要章节就下结论，
漏掉了引擎技术选型表、文件结构、`extraResources/sherpa/` 目录里的 VAD 与降噪模型、
以及 `docs/guides/engines/` 下的逐引擎说明。

**错在哪**：
**最关键的实现细节，往往不在 README 正文，而在目录结构和子文档里。**
`extraResources/sherpa/vad/silero_vad.onnx` 这个文件的存在本身，
就说明了「VAD 是内置的、独立于 ASR 模型」——这是架构信息，比 README 描述更硬。

**以后怎么做**：
- 调研一个项目，读完的判据是：**能画出它的数据流**，而不是「README 看过了」。
- 必读清单：README → 目录树（`git/trees?recursive=1`）→ 引擎/子模块文档 →
  核心实现文件 → 已知限制 → 测试与评测脚本。
- **测试脚本和评测脚本最能说明「作者在认真验证什么」**：
  SmartSub 有 `scripts/asr-review/` 一整套回归与回放工具，
  说明他们对自己引擎的表现做过系统评估，而不是凭感觉。

## L-006 别把「我这次没测出来」说成「这个方向没用」

三次判断失误的共同模式：

| 次 | 结论 | 真实原因 |
|---|---|---|
| 1 | 换引擎没用，砍掉 | 素材无信息量 |
| 2 | SenseVoice 更差 | 调用参数错（VAD 没传对） |
| 3 | 自建 provider 就行 | 技术选型错（该用 sherpa-onnx） |

**共同点：每次都是「方法有问题」，但我把它表述成了「对象有问题」。**

**以后怎么做**：
下结论前问自己一句：**「如果这个结论是错的，最可能错在哪？」**
如果答案是「我的测试方法」，那就先修方法，再下结论。
在没排除方法缺陷之前，结论一律写成「暂未观察到差异」，不写成「没有差异」。

## L-007 用同源素材验证「区分能力」等于没验证

**场景**：验证 sherpa 说话人分离的 `num_clusters`（强制人数）参数是否生效。

**当时的做法**：把同一段游戏音频的两个时间段（0-25s 和 60-85s）拼接，
当作「两个人」的测试素材，然后发现强制 `num_clusters=2` 仍只分出 1 人，
准备下结论「num_clusters 不生效」。

**错在哪**：
那是**同一个人的声音**。同一人不同时间段的声纹本来就高度相似，
聚类把它们归成一个人是**正确行为**，不是参数失效。
和 L-001 是同一个毛病的第二次发作：
**用不具备区分特征的素材，去测一个「区分能力」**，
然后拿「没区分出来」当作被质疑对象的缺陷。

真正的验证素材必须让**被测特征真的存在**：
要测「能否分辨两个人」，素材必须是两个不同的声音。
改用真人男声 + Windows TTS 女声之后，才拿到有意义的结论。

**为什么又犯**：
拼接两段音频「看起来像」两个说话人，我凭直觉就接受了这个类比，
没有停下来问「这两段的声纹距离真的够大吗」。

**以后怎么做**：
设计验证素材时，先问一句：**「这个素材里，我要测的特征真的存在吗？」**
- 测识别准确率 → 素材必须真的有语音（L-001）
- 测说话人区分 → 素材必须是不同的人
- 测降噪 → 素材必须真的有噪声

**通用化**：**任何「A 比 B 好 / 某功能不生效」的结论，前提是测试素材里
该差异/该功能确实可被观测。** 素材不满足前提时，结论只能写「无法验证」，
不能写成「没有效果」。

## L-008 第三方导出的模型仓库，README 往往不写清参数格式

**场景**：接入 Qwen3-ASR（sherpa-onnx 版）。

**当时的做法**：按直觉猜 tokenizer 参数，先后试了
`tokens.txt` 和 `tokenizer.json`，都是 404；代码里也就按「二选一文件」写。

**错在哪**：
实际情况是**目录**：`tokenizer/{vocab.json, merges.txt, tokenizer_config.json}`。
HF 仓库是第三方导出（`csukuangfj2`），其 README 只有三行，只说模型来自
ModelScope，**完全没有说 tokenizer 该怎么传**。
我拿「其他 sherpa 模型用 tokens.txt」的惯例去套，套错了。

**为什么没早点查清**：
	extbf{sherpa 自己的官方文档（k2-fsa.github.io）写得很清楚}，而且有完整文件清单
和代码示例。我应该先读官方文档再写代码，而不是照着别的模型的惯例猜。

**附带发现**：官方示例里 `max_new_tokens=1024`，而 Python 绑定的默认值只有 128。
Qwen3 是 LLM 结构，128 个 token 对稍长语音就会截断（字幕尾部丢失）。
**默认值不等于合理值**，接入新模型时要对照官方示例核对关键参数。

**以后怎么做**：
1. 接入第三方模型，**先读上游官方文档**，不要用同类模型的惯例推断。
2. 逐个核对关键参数（tokenizer 形态、max_new_tokens、采样参数），
   并在代码注释里写明「为什么是这个值 / 从哪里确认的」。
3. 仓库缺 README 说明时，去翻**导出脚本**或**官方文档**，
   而不是继续猜。

**通用化**：**惯例可以加速，但不能替代确认。** 尤其是「路径是文件还是目录」
这种一旦猜错就整个功能不可用、而且报错信息还指不到问题所在的细节。


## L-009 换参照物之前，不要急着否定新东西

**场景**：刚接入 Qwen3-ASR 时，我从第一段实测（粤语）看出
「Qwen3 把 my princess 写成 my princes、还多了个『产』字」，
几乎要下结论「Qwen3 不如 SenseVoice，不必引入」。

**实际数据**（同一批官方测试音频，重采样到 16k 后对比）：

| 场景 | Qwen3-ASR | SenseVoice |
|---|---|---|
| 粤语 | 似寻寻觅觅，终于揾到 my princess（对） | 次寻寻觅觅终于**稳到** my princes **产**（错） |
| 中英混说 | I'm alone... Je suis tout seul. Sono tuto.（法/意都对） | Is we two sell. そらとた。（乱码） |
| 中文绕口令 | 红鲤鱼、绿鲤鱼、**驴**的出租车司机（对） | 绿鲤鱼**与驴**的…骨质**疏通**症（错） |
| 英语说唱 | Why do I still write? Sometimes it's hard enough（完整） | While was still right sometimes it hard（崩了） |
| 日语 | 応えてきた | 答えてきた（两者都对，Qwen3 更贴原意） |

**结论完全相反**：除日语打平外，Qwen3 在**其余四项都明显更好**，
中英混说和英语说唱几乎是压倒性的。

**错在哪**：
我只看了**一段**素材的一个错字，就形成了印象。
单段素材的个别错字不构成能力判断 —— 尤其当那一段里
两者都各有一处错，我只是**先看到了 Qwen3 的那处**。

**代价也要说清**：Qwen3 慢 6~8 倍（4.0s vs 1.2s、4.2s vs 0.6s），
且模型 936MB。所以正确结论不是「换成 Qwen3」，
而是**「Qwen3 作为高质量选项，按素材类型选」**：
- 中文游戏喊话、快速出片 → SenseVoice
- 多语言、混说、说唱、有口音 → Qwen3

**以后怎么做**：
评价新方案时，**先跑满一组有代表性的场景再形成印象**，
并且把两边的结果**并排看**，而不是看完一边就先入为主。
单点样本只能提「疑问」，不能下「结论」。

**与 L-001/L-007 的关系**：那两条讲「素材不满足前提」，
这条讲「样本量不足 + 先看到谁」。同一个病根的第三种形态：
**用不足以支撑结论的证据下结论。**

## L-010 「没做」不等于「不需要做」

**场景**：评估要不要做字体逐字回退（缺字时自动换字体）。

**当时的判断**：写了一句「字体解析不值得做，libass 本身会按候选链找字体」，
然后跳过了。

**错在哪**：
对方 `fontResolver.ts` 有 **916 行**。
一个功能如果一句话就能说清「不需要」，它不会有 916 行。

我的理由（libass 会回退）不是完全错 —— 但 libass 的候选链要求
**用户自己在系统里装好那个字体**，而且无法处理「主字体只缺个别字」的情况。
916 行说明对方踩过大量坑：CJK 覆盖、TTC 集合、隐形字符、变体字。

**真正的错误在于推理方向**：
我用「理论上有个机制可能覆盖」否定了「对方投入了 916 行」。
这是**用可能性否定已发生的事实**。

**以后怎么做**：
看到对方在某处投入大量代码，**默认它解决了真问题**，先去读它在解决什么，
再判断我们是否需要。想跳过时，必须能说出「对方那 916 行具体在防什么坑，
而我们因为什么理由不会遇到那些坑」—— 说不出就是没查清。

**这条的实际代价**：这一轮补做时踩了 TTC 偏移和丢字两个坑，
恰好就是那 916 行在防的东西。

## L-011 「静默降级」比报错危险得多

**场景**：非 ASCII 路径导致 sherpa-onnx 模型打不开。

**症状**：不是崩溃，不是异常 —— 是 silero VAD 构造失败后
每次调用打印一行 `vad is nullptr`，然后**永远切出 0 个语音段**。

更早的一个同类案例（本项目已修）：`extract_audio` 用固定的临时文件名，
视频路径不存在时，它读到了**上一个任务残留的音频**，
于是输出了 3 条看似合理的字幕。

**共同点**：两者都「正常返回」，都产出了**看起来对、实际全错**的结果。
这类问题比抛异常危险得多，因为：
- 没有错误日志可搜
- 用户只会说「识别不出来」，不说「报了什么错」
- 自动化测试如果只断言「不抛异常」，全部会通过

**以后怎么做**：
1. 任何「降级」路径都必须**留下可观测痕迹**（日志/返回字段），不能静默
2. 测试要断言**产出内容的合理性**，不能只断言「没抛异常」
   （`test_glyph_fallback` 里「去标签后必须与原文逐字一致」就是这种约束）
3. 临时文件一律用唯一名 + 用完清理，绝不复用固定路径

## L-012 测试「一次只报一个缺失」会掩盖系统性问题

**场景**：`SettingsPage.test.tsx` 的 `vi.mock('../api')` 缺 5 个导出。

**现象**：每次跑只报一个 `No "xxx" export is defined`，
补上再跑，报下一个。五轮才补完。

**根因**：vitest 的全量 mock 是**遇到第一个缺失就抛**，
所以「缺 5 个」和「缺 1 个」的表现完全一样。

**以后怎么做**：
遇到「补一个又冒一个」的循环，**立刻停止逐个试**，改成一次性扫描：
从被测文件里把实际 import 的名字全提取出来，与 mock 块做差集。
（`C:/tmp/fixall.py` 就是这么做的，一次找到全部 5 个。）

同理适用于：TS 编译错误、lint、依赖缺失 —— 凡是一次只报一个的工具，
都应该用脚本做批量比对而不是人工迭代。

## L-013 改测试断言前先判定「是实现错了还是测试错了」

**场景**：`test_llm_providers.test_every_provider_is_usable` 在这轮挂了，
因为新增的 `tencent_free` 协议不在白名单 `("openai","deepl","google")` 里。

**判定依据**：
- 实现侧：`tencent_free` 确实不需要 base_url、不需要模型名，
  只需要一个说明页链接 —— 与 DeepL/Google 同类，是**合法的新协议**
- 测试侧：白名单是硬编码的三个值，新增协议时没跟上

所以是**测试没跟上契约扩展**，不是实现错了。改白名单是对的。

**反例警示**：
如果当时是「实现返回了错误的字段」，为了让测试变绿而去改断言，
那就是把 bug 固化进测试里。两者表现一样（都是改测试），性质完全相反。

**以后怎么做**：改任何测试断言前，必须能写出这两句话：
1. 实现的行为**应该**是什么（依据是什么）
2. 当前实现的行为是什么（观测到什么）
两者不一致时，**先判断哪边符合设计意图**，再决定改哪边。
写不出这两句就是还没查清。
