## 一、项目概述

### 1.1 项目定位

**SubAI Translator** 是一款AI视频字幕识别与翻译软件,支持语音字幕识别(ASR)和硬字幕OCR识别,提供多格式输出和术语库管理功能。

### 1.2 核心功能

- ✅ 语音字幕识别 (Whisper/faster-whisper)
- ✅ 硬字幕OCR识别 (RapidOCR)
- ✅ 多格式输出 (SRT/VTT/ASS/JSON)
- ✅ 双语字幕生成
- ✅ 术语库管理 (SQLite + JSON)
- ✅ CLI命令行工具
- ✅ FastAPI后端服务
- ✅ 完整测试套件

### 1.3 技术栈

| 组件 | 技术选型 |
|------|----------|
| 开发语言 | Python 3.9-3.12 |
| 语音识别 | faster-whisper |
| OCR识别 | RapidOCR |
| 翻译服务 | koboldcpp (本地LLM) |
| API框架 | FastAPI |
| 数据存储 | SQLite |
| 测试框架 | pytest |
| 视频处理 | FFmpeg 5.0+ |

4. **GPU支持**: 当前版本主要使用CPU推理,GPU加速未启用
5. **并发处理**: 不支持多视频并发处理
6. **前端界面**: 仅提供CLI和API,无GUI界面

### 11.3 额外方向（搁置）：实时屏幕悬浮翻译

**状态**: ⏸️ 搁置（2026-09-29 评估后决定暂不实施;结论与重启条件保留于此,避免重复讨论）

**设想**: 不下载、不上传文件,直接读取屏幕上正在播放的画面,实时识别并翻译,以**悬浮字幕层（Overlay HUD）**叠加显示。面向在线观看、网课、游戏等拿不到文件的场景。

**技术链路**: 截屏（框选 ROI）→ OCR → 去重/稳定判定 → 翻译 → 透明置顶穿透窗口叠加。

**可行性结论**:
- 技术可行,且能复用本项目已有资产（RapidOCR、翻译层、术语库、翻译缓存、Tauri 壳）,`hardsub_segments` 的合并去重逻辑已覆盖大半链路。
- 延迟预算（依据本项目实测:OCR 720p 全帧 0.201s/帧、本地 LLM 翻译 ≈0.89s/行）估算为端到端 **1.0–2.5s**（本地 LLM）或 0.8–1.5s（云端）。本质是"延迟直播字幕",瓶颈在翻译与稳定判定,不在 OCR。

**硬约束（重启前必须实测）**:
1. DRM 黑屏:浏览器中受保护播放（Netflix / Disney+ 等）通常只能抓到黑帧。
2. 独占全屏或部分硬件叠加路径抓不到、叠加异常,需无边框窗口化。
3. 悬浮层要跟随窗口移动/缩放/全屏/多显示器/DPI 缩放。
4. 实时为碎片逐句翻译,质量低于文件模式的带上下文批量翻译。
5. 抓屏 + OCR + LLM 与视频解码争抢 CPU/GPU,笔记本掉帧发热。
6. 法律/ToS 灰区（个人观看辅助 vs 录制分发）。

**参考实现（学思路,不搬代码）**: Translumo（Apache-2.0,**C#/.NET/WPF**,约 5.8k stars,仓库无 NOTICE）。可借鉴结论:框选 ROI、必须无边框/窗口化、多 OCR 引擎打分择优、低延迟链路设计。

**不可直接搬运的原因**: 技术栈不同（C#/.NET vs Python + Rust/React）。许可证 Apache-2.0 本身允许修改、闭源再分发与商用（需附 LICENSE、保留声明、标注修改、不得使用其商标;非营利同样适用）,**真正的障碍是跨语言复用等于重写,达不到"省力"目的**。故定位为参考实现与竞品基线,不并入;若重启则在本项目栈内独立实现。

**重启决策门（全部满足才做）**:
1. 10 个真实片源中 ≥8 个可正常捕获（非黑屏）
2. 端到端延迟 P50 ≤1.5s、P95 ≤2.5s
3. 字幕行字符级准确率 ≥90%（画面清晰、ROI 正确时）
4. 连续运行 30 分钟不崩、不明显掉帧
5. 复用同一套翻译/术语/缓存,不产生第二套逻辑

先行步骤（1–2 天,不碰主线、不写 UI）:命令行打通"框选→OCR→翻译",只输出延迟与准确率实测数据。

**更小的备选**: 浏览器扩展（读取页面内现成字幕轨或对页面局部 OCR）,成本低一个数量级,但仅覆盖浏览器,对硬字幕与受保护内容无效。

#### v3.3.7 (2026-10-01) —— 修复"配音静音"：合成成功 ≠ 合成出声音

**问题**:目标语言没有匹配的 TTS 音色时,程序回落到默认音色;**若该音色不支持字幕语言,会合成出"只有文件头、0 采样"的音频**。而 `synthesize_segments` 会把静音补齐到字幕时间轴,于是"总时长/最大同步偏差"全都正常,用户拿到一条**全静音配音**却毫无提示。

| 中文 + 中文音色 | Microsoft Huihui | 124,342 B | 2.590 s ✅ |

**验证（打包版实测）**:

|---|---|
| 显式英文音色读中文 | `voice_matched=True`、**`silent_clips=2`**（`total=3.0s / drift=0.0s` 依然"正常"）|

**测试**:后端 **314**（+6:3 项静音检测单测 + 3 项接口测试,含"正常音频不误报"的反向用例）;前端 **34**（+3）。

#### v3.2.0 (2026-10-01) —— 协作式取消：取消任务真正会停下

**问题**:`DELETE /api/task/{id}` 之前只是把数据库状态改成 `cancelled` —— **跑起来的流水线并不会停**（代码注释也承认"实际停止依赖 pipeline 协作检查",而那个检查并不存在）。用户看到"已取消",后台仍在烧 CPU/GPU。

**根因**:任务通过线程池执行,Python 无法安全强杀线程;必须由执行方在检查点主动退出。

**实现**:
- 新增 `src/cancel.py`:线程安全的取消令牌注册表（`register / cancel / is_cancelled / unregister`）+ `TaskCancelled` + `raise_if_cancelled()`。
- `pipeline.run_pipeline(..., should_cancel=...)` 在 4 个检查点轮询:**抽音轨前 / 识别完成后 / 每个翻译批次前 / 写盘前**;`translate()` 同样接受该参数。取消发生在写盘前 → **不产生半成品文件**。
- `server.process_transcode_task` 注册令牌并传入 `should_cancel`;新增 `except TaskCancelled` 分支,标记 cancelled 后 **return（不 re-raise）**,避免任务队列的异常分支把它覆盖成 failed。
- `DELETE /api/task/{id}` 现在会置位令牌,响应里返回 `signalled`（是否真的命中了在跑的任务）。

**边界（诚实说明）**:最坏情况是"当前这一步跑完才停"——例如 ASR 推理本身不可中断;这与"硬中止线程"是两回事,端点说明与代码里都写清楚了。

**测试与真实验证**:
- `tests/test_cancel.py`（7 项）:注册表语义、取消时**零 LLM 请求**、批次间立即停止（实测完成 1 批后停）、`run_pipeline` 在重活前取消且不创建输出目录。
- 打包版实测（真实 API）:
  - 提交后立即取消 → `cancelled`、`signalled=true`、**无产物**;
  - 运行 3 秒（ASR 期间）再取消 → `cancelled`、**无产物**;
  - 不取消 → `completed`（`任务完成（3 行 · 术语命中 0 · 缓存命中 3）`）,正常路径未被破坏;
  - 后端日志留痕:`任务 XXX 已被用户取消（协作式中止）`。

**顺带修复**:`test_e2e.py` 的翻译服务 fixture 原本在真实服务不可用时 **skip**,导致 CI 里 asr/hardsub/VTT/ASS/JSON 多格式端到端覆盖永久缺失。现改为**降级到本地 mock**,用例始终执行。

**验证**: 全量 **279 passed / 0 skipped**（koboldcpp 已关闭的情况下仍零跳过）。

#### v3.1.1 (2026-10-01) —— 翻译失败降级 + 修复 .env 导致后端启动崩溃（严重）

- **现象**: 项目根存在 `.env` 时,打包后端启动即崩溃 —— `pydantic ValidationError: extra_forbidden`,键为 `subai_llm_mode` / `subai_llm_cloud_model`。
